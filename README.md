# Система аутентификации и авторизации

Backend-приложение с собственной системой управления доступом к ресурсам на основе ролей (RBAC). Аутентификация и проверка прав реализованы вручную, без готовых решений «из коробки»: собственная JWT-аутентификация через middleware и собственный класс проверки прав, сверяющийся с таблицей правил в базе данных.

## Стек

- Python 3.12
- Django 5.2
- Django REST Framework
- PostgreSQL
- PyJWT

## Архитектура

Проект разделён на два приложения по зоне ответственности:

- **`authentication`** — аутентификация: модель пользователя, регистрация, вход, выход, профиль, middleware для опознания пользователя по токену.
- **`access`** — авторизация: роли, ресурсы, правила доступа, класс проверки прав, mock-эндпоинты бизнес-объектов, API управления правилами.

Граница между приложениями повторяет смысловую границу: аутентификация (кто ты) отделена от авторизации (что тебе можно).

## Установка и запуск

1. Клонировать репозиторий и перейти в каталог проекта.

2. Создать и активировать виртуальное окружение:
   ```bash
   python -m venv venv
   source venv/bin/activate
   ```

3. Установить зависимости:
   ```bash
   pip install -r requirements.txt
   ```

4. Создать файл `.env` на основе `.env.example` и заполнить значения:
   ```bash
   cp .env.example .env
   ```

5. Создать базу данных в PostgreSQL:
   ```sql
   CREATE DATABASE access_control;
   CREATE USER access_user WITH PASSWORD 'ваш_пароль';
   GRANT ALL PRIVILEGES ON DATABASE access_control TO access_user;
   \c access_control
   GRANT ALL ON SCHEMA public TO access_user;
   ```

6. Применить миграции:
   ```bash
   python manage.py migrate
   ```

7. Загрузить тестовые данные:
   ```bash
   python manage.py loaddata fixtures/access_data.json
   python manage.py loaddata fixtures/auth_data.json
   ```

8. Запустить сервер:
   ```bash
   python manage.py runserver
   ```

## Схема базы данных и система прав

Система управления доступом построена на трёх связанных таблицах.

### Role — роли

Список ролей в системе: `admin`, `manager`, `user`, `guest`. Каждый пользователь ссылается на одну роль (поле `role` в модели пользователя, связь «многие к одному»). Одна роль на пользователя выбрана осознанно: роли иерархичны и взаимоисключающи (admin включает права manager, manager включает права user), поэтому несколько ролей на одного пользователя не требуются.

### Resource — типы защищаемых объектов

Справочник типов объектов, к которым применяются права: `item`, `order`, `seller`, `review`, `access_rule`. Это не сами объекты, а их категории. Реальные таблицы бизнес-объектов не создаются — они представлены mock-эндпоинтами.

### AccessRule — правила доступа

Связующая таблица между ролью и типом ресурса. Каждая строка отвечает на вопрос «что роль X может делать с типом объекта Y». На пару (роль, ресурс) приходится не более одного правила — это гарантируется ограничением уникальности на уровне базы.

Права хранятся булевыми полями. Для действий над существующими объектами каждое право имеет две версии:

| Поле | Значение |
|------|----------|
| `create_permission` | может создавать объекты этого типа |
| `read_permission` | может читать **свои** объекты |
| `read_all_permission` | может читать **любые** объекты (в том числе чужие) |
| `update_permission` | может изменять **свои** объекты |
| `update_all_permission` | может изменять **любые** объекты |
| `delete_permission` | может удалять **свои** объекты |
| `delete_all_permission` | может удалять **любые** объекты |

Разделение «свои / любые» — ядро системы. Право без суффикса `_all` разрешает действие только над объектами, которые пользователь создал сам (определяется по полю владельца `owner`). Право с суффиксом `_all` разрешает действие над объектами любого владельца. У `create` версии `_all` нет: при создании объекта владельца ещё не существует, делить на «свой / чужой» нечего.

### Коды ответов

- **401 Unauthorized** — пользователь не опознан (нет токена, токен недействителен или просрочен). Провал аутентификации.
- **403 Forbidden** — пользователь опознан, но у его роли нет прав на запрашиваемое действие с ресурсом. Провал авторизации.

## Аутентификация

Аутентификация построена на JWT, который создаётся вручную через PyJWT.

При входе сервер проверяет email и пароль, и выдаёт токен. В полезной нагрузке токена хранятся только идентификатор пользователя, версия токена и срок истечения — никаких чувствительных данных, поскольку полезная нагрузка JWT доступна для чтения любому держателю токена (подпись защищает от подделки, но не скрывает содержимое).

Опознание пользователя на каждом запросе выполняет кастомный middleware: он читает токен из заголовка `Authorization: Bearer <token>`, проверяет подпись и срок действия, находит пользователя и устанавливает `request.user`. При отсутствии токена middleware не вмешивается (это позволяет работать сессионной аутентификации админки); при недействительном токене пользователь становится анонимным.

DRF связан с middleware через тонкий класс аутентификации, который сообщает DRF об уже опознанном пользователе. Это также устраняет проверку CSRF, не нужную для stateless-API на токенах.

### Выход и инвалидация токенов

У каждого пользователя есть счётчик версии токена (`token_version`), который записывается в полезную нагрузку при выдаче токена. При выходе из системы счётчик увеличивается, и все ранее выданные токены перестают проходить проверку версии в middleware. Таким образом выход инвалидирует токен на стороне сервера, а не только удаляет его у клиента.

## Авторизация

Проверку прав выполняет кастомный класс, подключённый глобально для всех эндпоинтов. Логика проверки:

1. Если пользователь не опознан — ответ 401.
2. Суперпользователь проходит проверку без обращения к таблице правил.
3. Действие определяется по HTTP-методу (`GET` → read, `POST` → create, `PUT`/`PATCH` → update, `DELETE` → delete).
4. По роли пользователя и ресурсу эндпоинта находится правило в таблице `AccessRule`.
5. Проверяется соответствующий флаг. Для операций над конкретным объектом дополнительно сравнивается владелец: для своего объекта достаточно базового права, для чужого требуется право с суффиксом `_all`.

Эндпоинт изменения правил доступа защищён отдельной проверкой и доступен только пользователям с ролью `admin`.

## Эндпоинты API

| Метод | Путь | Назначение | Доступ |
|-------|------|------------|--------|
| POST | `/api/register/` | Регистрация (email, имя, фамилия, отчество, пароль, повтор пароля) | Все |
| POST | `/api/login/` | Вход по email и паролю, выдача JWT | Все |
| POST | `/api/logout/` | Выход, инвалидация токена | Аутентифицированные |
| GET | `/api/profile/` | Просмотр своего профиля | Аутентифицированные |
| PATCH | `/api/profile/` | Обновление своего профиля | Аутентифицированные |
| DELETE | `/api/profile/` | Мягкое удаление аккаунта (`is_active=False`) | Аутентифицированные |
| GET | `/api/orders/` | Список заказов (mock, с фильтрацией по правам) | По правилам |
| GET | `/api/orders/<id>/` | Конкретный заказ (mock, проверка владельца) | По правилам |
| GET | `/api/reviews/` | Список отзывов (mock, с фильтрацией по правам) | По правилам |
| GET | `/api/reviews/<id>/` | Конкретный отзыв (mock, проверка владельца) | По правилам |
| GET, POST | `/api/rules/` | Просмотр и создание правил доступа | Только admin |
| GET, PUT, PATCH, DELETE | `/api/rules/<id>/` | Управление конкретным правилом | Только admin |

## Тестовые данные

Фикстуры содержат четыре роли (`admin`, `manager`, `user`, `guest`), пять ресурсов и набор правил, демонстрирующих разные уровни доступа: гость только читает, пользователь управляет своими объектами, менеджер получает права над чужими объектами (`_all`), администратор имеет полный доступ и управляет правилами.

## Примеры запросов

Вход и получение токена:
```bash
curl -X POST http://127.0.0.1:8000/api/login/ \
  -H "Content-Type: application/json" \
  -d '{"email": "test@gmail.com", "password": "Testpass2026"}'
```

Запрос с токеном:
```bash
curl http://127.0.0.1:8000/api/orders/ \
  -H "Authorization: Bearer <полученный_токен>"
```

Обновление правила доступа администратором:
```bash
curl -X PATCH http://127.0.0.1:8000/api/rules/5/ \
  -H "Authorization: Bearer <токен_администратора>" \
  -H "Content-Type: application/json" \
  -d '{"delete_all_permission": true}'
```

## Принятые решения

- **Одна роль на пользователя** вместо связи «многие ко многим» — роли иерархичны, множественные роли усложнили бы систему без практической пользы.
- **Аутентификация в middleware** — опознание пользователя вынесено в middleware, как единая точка для всех запросов; DRF связан с ним через класс аутентификации.
- **Stateless JWT с версионированием** — выход реализован через счётчик версии токена, что даёт серверную инвалидацию без хранения списка активных сессий.
- **Секреты в переменных окружения** — `SECRET_KEY` и параметры БД вынесены в `.env`, который не попадает в репозиторий; шаблон значений — в `.env.example`.
